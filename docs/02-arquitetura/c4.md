# Diagramas C4

> **Responde a:** quais sistemas e containers existem? como a API se divide por dentro? onde moram as regras e a estatística? onde entra o simulador? como seria um backtest sem HTTP e sem banco?

## 1. Contexto

```mermaid
C4Context
    title Contexto: motor antifraude Pix

    Person(risco, "Time de risco", "Calibra regras e lê as análises")
    System_Ext(pagamento, "Sistema de pagamento Pix", "Banco cliente ou a banca do hackathon: manda o Pix antes de liquidar")

    System(motor, "Motor antifraude Pix", "Recebe o Pix, decide approved / two_factor_required / rejected e grava a análise com o motivo")

    System_Ext(med, "MED e contestações (futuro)", "Desfecho real da fraude: viraria rótulo")
    System_Ext(twofa, "Fluxo de 2FA (futuro)", "Confirmação do cliente: rótulo fraco e imediato")

    Rel(pagamento, motor, "POST /pix/transaction, GET /pix/transaction/{id}", "HTTPS + INTERNAL-TOKEN")
    Rel(risco, motor, "Simula tráfego e calibra parâmetros", "scripts/simulate.py")
    Rel(med, motor, "Rótulos atrasados (fora do escopo)")
    Rel(twofa, motor, "Resultado do 2FA (fora do escopo)")
```

O motor não chama nada de fora no caminho da decisão ([ADR 0002](decisoes/0002-monolito-sincrono-sem-dependencia-externa.md)). MED e 2FA aparecem só como a origem futura dos rótulos.

## 2. Containers

```mermaid
C4Container
    title Containers: o que roda separado

    System_Ext(pagamento, "Sistema de pagamento Pix", "Cliente da API")
    Person(risco, "Time de risco")

    System_Boundary(motor, "Motor antifraude Pix") {
        Container(api, "api", "Python 3.11, FastAPI, SQLAlchemy 2", "Valida o contrato, carrega o histórico, roda as 17 regras, decide e grava")
        ContainerDb(db, "db", "PostgreSQL 16", "pix_transaction, pix_analysis, pix_analysis_reason, analysis_status (append-only)")
    }

    Container(sim, "Simulador", "Python, requests (scripts/simulate.py)", "Gera Pix legítimos e fraudes rotuladas, manda pela API em ordem cronológica e mede fricção, captura e latência")
    Container(tests, "Suíte de testes", "pytest (tests/)", "Black box por HTTP: cada regra, cada cenário, contrato e idempotência")

    Rel(pagamento, api, "POST/GET /pix/transaction", "HTTP/JSON")
    Rel(api, db, "Consultas por janela e INSERT", "SQL")
    Rel(risco, sim, "make simulate")
    Rel(sim, api, "Milhares de POST com rótulo guardado no script", "HTTP/JSON")
    Rel(tests, api, "POST/GET", "HTTP/JSON")
    Rel(tests, db, "Só zera o banco entre execuções", "SQL")
```

O simulador e os testes ficam fora do `docker-compose.yml`: rodam na máquina de quem desenvolve, contra a `api` de pé ([estratégia de testes](../07-testes/estrategia.md), [ADR 0020](decisoes/0020-simulador-para-calibracao.md)).

## 3. Componentes da API

```mermaid
C4Component
    title Componentes da api: camadas do Base Service + motor

    Container_Ext(cliente, "Cliente HTTP", "Sistema de pagamento, simulador ou pytest")
    ContainerDb_Ext(db, "db", "PostgreSQL 16")

    Container_Boundary(api, "api") {
        Component(mw, "Middlewares", "src/middlewares/", "Request id, log, INTERNAL-TOKEN (403), sessão de banco")
        Component(schema, "SchemaHandler", "src/utils/schema_handler.py + src/schemas/", "JSON Schema fechado do payload (400)")
        Component(resource, "PixTransactionResource", "src/resources/", "HTTP de entrada e saída; 201 ou 200")
        Component(controller, "PixTransactionController", "src/controllers/", "Idempotência, snapshot, contexto, roda as regras, decide, commit")
        Component(repo, "PixTransactionRepository", "src/repositories/", "Busca por pix_id, agregados por janela, INSERT")
        Component(engine, "Motor de regras", "src/rules/", "PixSnapshot, RuleContext, ACTIVE_RULES, severidade")
        Component(dto, "PixAnalysisDTO", "src/dtos/", "{key, status, metadata}")
        Component(errors, "Erros QIT", "src/errors/", "404 QIT002001, 409 QIT002002")
    }

    Rel(cliente, mw, "HTTP")
    Rel(mw, schema, "")
    Rel(schema, resource, "payload válido")
    Rel(resource, controller, "analyze / get_by_pix_id")
    Rel(controller, repo, "agregados e gravação")
    Rel(repo, db, "SQL")
    Rel(controller, engine, "evaluate(pix, context) em todas as regras")
    Rel(controller, dto, "monta a resposta")
    Rel(controller, errors, "levanta recusa")
```

A dependência anda num sentido só ([camadas](camadas.md)). O motor de regras não conhece repository nem banco: recebe tudo pronto no `RuleContext` ([ADR 0005](decisoes/0005-regras-puras-com-contexto-carregado.md)).

## 4. Componentes do motor de regras

```mermaid
C4Component
    title Componentes do motor: regras, sinais e estatística

    Component_Ext(controller, "PixTransactionController", "src/controllers/", "Monta snapshot e contexto, agrega por severidade")

    Container_Boundary(rules, "src/rules/ + src/utils/statistics.py") {
        Component(snapshot, "PixSnapshot", "pix_snapshot.py", "Pix parseado; self-transfer; CPF ou CNPJ")
        Component(context, "RuleContext", "rule_context.py", "Agregados de histórico por janela, imutável")
        Component(registry, "ACTIVE_RULES", "__init__.py", "17 regras com parâmetros RULE_* de constants.py")
        Component(det, "Regras determinísticas", "limit_*, velocity_source_count, velocity_device_sources, amount_*, profile_new_*, counterparty_*", "Limites, contagens e idades com corte fixo")
        Component(stat, "Regras estatísticas", "profile_amount_robust_z, velocity_poisson_gamma, profile_geo_velocity", "Perfil do próprio pagador (ADR 0016)")
        Component(typo, "Tipologias", "typology_account_takeover, typology_mule, typology_splitting", "Combinações que descrevem um golpe: rejected (ADR 0018)")
        Component(signals, "Sinais compartilhados", "signals.py", "amount_z, geo_speed_kmh: mesmo cálculo para perfil e tipologia")
        Component(statistics, "Estatística pura", "src/utils/statistics.py", "robust_z (mediana/MAD), cauda binomial negativa (Poisson-Gamma), haversine")
        Component(decision, "Severidade", "decision.py", "approved 0 < two_factor_required 1 < rejected 2")
    }

    Rel(controller, registry, "itera todas")
    Rel(registry, det, "")
    Rel(registry, stat, "")
    Rel(registry, typo, "")
    Rel(det, snapshot, "lê")
    Rel(det, context, "lê")
    Rel(stat, signals, "usa")
    Rel(typo, signals, "usa")
    Rel(signals, statistics, "usa")
    Rel(controller, decision, "maior severidade vence")
```

Tudo dentro desta caixa é Python puro: sem banco, sem ambiente, sem relógio. É essa pureza que permite o backtest da seção seguinte reutilizar o motor sem mudar uma linha das regras.

## 5. Proposta: backtest sem HTTP e sem banco

**Estado:** fora do escopo desta entrega ([ADR 0017](decisoes/0017-ml-fora-do-prazo-e-do-hot-path.md)). Fica desenhado para mostrar que a arquitetura comporta.

O backtest atual é o simulador pela API: fiel, mas cada Pix paga o HTTP e as cerca de 15 consultas SQL (~45 ms). Para reprocessar milhões de Pix reais, o motor roda em lote, direto em Python. O risco é duplicar a lógica dos agregados (uma versão em SQL, outra em Python) e a calibração medir uma cópia do motor (*training-serving skew*). A proposta evita isso com uma **porta de histórico** e um **teste de paridade**:

```mermaid
C4Container
    title Proposta: backtest em lote reutilizando o mesmo motor

    Person(risco, "Time de risco")
    ContainerDb_Ext(arquivo, "events.jsonl", "Arquivo", "Pix em ordem cronológica + rótulo (sintético do simulador ou real: MED, contestação)")

    System_Boundary(bt, "Backtest em lote (scripts/backtest.py)") {
        Container(runner, "Runner", "Python", "Lê eventos, monta PixSnapshot, pede o contexto, avalia, grava a decisão no histórico em memória, compara com o rótulo")
        Container(mem, "InMemoryHistory", "Python", "Implementa HistoryPort com índices em memória por pagador, aparelho e destino")
        Container(report, "Relatório", "Markdown/JSON", "Fricção, captura por tipologia, fronteira por parâmetro")
    }

    System_Boundary(shared, "Código compartilhado com a api (sem alteração)") {
        Container(core, "Motor de regras", "src/rules/ + src/utils/statistics.py", "PixSnapshot, RuleContext, ACTIVE_RULES, severidade")
        Container(port, "HistoryPort", "Interface Python", "Os agregados que o RuleContext precisa, com a mesma semântica de janela [t - N, t)")
    }

    System_Boundary(prod, "api (produção)") {
        Container(sqladapter, "PixTransactionRepository", "SQLAlchemy", "Implementa HistoryPort com SQL indexado")
    }

    Container(parity, "Teste de paridade", "pytest", "Mesmo roteiro de Pix nos dois adaptadores: todo agregado precisa sair igual")

    Rel(risco, runner, "roda com um conjunto de parâmetros")
    Rel(runner, arquivo, "lê")
    Rel(runner, core, "evaluate em todas as regras")
    Rel(runner, mem, "contexto e gravação")
    Rel(mem, port, "implementa")
    Rel(sqladapter, port, "implementa")
    Rel(parity, mem, "compara")
    Rel(parity, sqladapter, "compara")
    Rel(runner, report, "gera")
```

O que precisaria mudar no código para isso existir:

| Mudança | Por quê |
|---|---|
| Extrair a montagem do `RuleContext` e o `_decide` do controller para `src/rules/engine.py` (`analyze(snapshot, history) -> decisão, motivos, sinais`) | Hoje essa orquestração mora no controller, que depende de sessão de banco. O runner e o controller passam a chamar a mesma função |
| Definir `HistoryPort` com os métodos de agregado que o repository já tem | Uma interface, dois adaptadores: SQL na api, memória no backtest |
| `InMemoryHistory` em `scripts/` | Agregados em memória, alimentados pelo próprio runner na ordem cronológica |
| Teste de paridade que roda o mesmo roteiro contra os dois adaptadores | Garante que "quantos Pix na janela" dá o mesmo número nos dois lados. Sem ele, a segunda implementação diverge em silêncio |

Ganho esperado: cada Pix deixa de pagar HTTP e consultas, e o lote passa de minutos para segundos, o que viabiliza grid de parâmetros e, um dia, gerar a base de treino de um modelo. Preço: uma segunda implementação dos agregados, contida pelo teste de paridade.
